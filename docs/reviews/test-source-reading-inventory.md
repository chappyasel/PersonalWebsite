# Source-reading tests: inventory and migration batches

Generated by `node scripts/test-source-reads.mjs`. Rerun it after any batch to
get the current numbers. The script sorts everything, so two runs over the same
tree produce byte-identical output.

A batch is one source file plus every test that reads it. Closing a batch means
that source file's behavior became reachable through an interface, and its
tests now call it.

## Recommended order

**1. SceneDiagnostics.tsx (202).** The largest batch and the least behavioral.
Most of it asserts that a control label or an element exists somewhere in a
2,195-line panel. The panel is DOM, and this repo already renders DOM
components with `renderToStaticMarkup` (see `BootScreen.test.tsx`), so the
whole batch can move to rendered-output assertions once the panel's
`createPortal` and effect paths are reachable from a server render. Three
sub-steps that pay off on their own: pull the control-and-label table out as
data (a list of `{ id, label, read, write }`), test that the table drives the
panel, then assert the panel's controls against the table instead of against
its source. `qualityReadout.ts`, added in this tranche, is the shape to copy.
Overlaps the diagnostics-registry task, so coordinate before starting.

**2. CoordinationGlobe.tsx (166).** One test file against one component.
Nearly all of it is geometry and material policy, which is what
`coordinationGlobeGeometry.ts` and `coordinationGlobeLegibility.ts` already
hold for their share. Extend those two rather than adding a third module, then
delete the source reads.

**3. StacksCanvas.tsx (165).** The hardest batch, and the one to do last. The
component is 1,991 lines wrapped around `<Canvas>`, so it cannot render in
Node, and much of what these tests assert is genuine wiring: a listener gets
installed, a callback publishes a trace event. Two pieces can move out first,
the quality-sample and lifecycle callbacks (pure functions over a snapshot) and
the resolution-step arithmetic. What remains is a short list of wiring facts
that should stay as source reads, clearly labelled as such. Overlaps the
boot-state task.

**4. TouchInteractionLayer.tsx (70).** Real event-handling policy: which
pointer types reach the scene, when a scroll beats a drag. It has a natural
pure interface (event shape in, intent out) and no rendering dependency. Good
first batch for someone new to this work.

**5. Meadow.tsx (50) and SceneEnvironment.tsx (43).** These read shader source.
Treat a shader string as the module's OUTPUT rather than its implementation:
assert against an exported shader constant instead of against the file. That
converts the reads without inventing an interface the GPU does not have.

**6. Everything at 44 and below.** The unit components (`UnitAbout`,
`UnitBlog`, `UnitProjects`, `UnitTraining`, `UnitSystems`, `ProjectArtifacts`)
share one shape: the test wants to know what a shelf places and where. Do them
together behind one placement-and-interaction interface rather than one at a
time.
