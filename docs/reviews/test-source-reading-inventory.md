# Source-reading tests: a heuristic lower-bound report

Generated by `node scripts/test-source-reads.mjs`, also `yarn
report:test-source-reads`. Rerun it after any batch to get the current numbers.
The script sorts everything, so two runs over the same tree produce
byte-identical output.

Read the counts as a **lower bound, not a measurement**. The script matches
reads by pattern, not by resolving types, so a source string that crosses a
file boundary or reaches `expect()` through a shape the patterns do not spell
goes uncounted. It never counts something that is not a real read, so the true
number is this one or higher. Two files it cannot attribute are corrected by
hand under "What the script cannot count"; those corrections are not in the
totals. It is a report, never a gate: it always exits zero and knows nothing
about a budget or a previous run.

A batch is one source file plus every test that reads it. Closing a batch means
that source file's behavior became reachable through an interface, and its
tests now call it.

## Recommended order

**1. SceneDiagnostics.tsx (201).** The largest batch and the least behavioral.
Most of it asserts that a control label or an element exists somewhere in a
2,195-line panel. The panel is DOM, and this repo already renders DOM
components with `renderToStaticMarkup` (see `BootScreen.test.tsx`), so the
whole batch can move to rendered-output assertions once the panel's
`createPortal` and effect paths are reachable from a server render. Three
sub-steps that pay off on their own: pull the control-and-label table out as
data (a list of `{ id, label, read, write }`), test that the table drives the
panel, then assert the panel's controls against the table instead of against
its source. `qualityReadout.ts`, added in this tranche, is the shape to copy.
Overlaps the diagnostics-registry task, so coordinate before starting.

**2. CoordinationGlobe.tsx (166).** One test file against one component.
Nearly all of it is geometry and material policy, which is what
`coordinationGlobeGeometry.ts` and `coordinationGlobeLegibility.ts` already
hold for their share. Extend those two rather than adding a third module, then
delete the source reads.

**3. StacksCanvas.tsx (165).** The hardest batch, and the one to do last. The
component is 1,991 lines wrapped around `<Canvas>`, so it cannot render in
Node, and much of what these tests assert is genuine wiring: a listener gets
installed, a callback publishes a trace event. Two pieces can move out first,
the quality-sample and lifecycle callbacks (pure functions over a snapshot) and
the resolution-step arithmetic. What remains is a short list of wiring facts
that should stay as source reads, clearly labelled as such. Overlaps the
boot-state task.

**4. TouchInteractionLayer.tsx (70).** Real event-handling policy: which
pointer types reach the scene, when a scroll beats a drag. It has a natural
pure interface (event shape in, intent out) and no rendering dependency. Good
first batch for someone new to this work.

**5. Meadow.tsx (50) and SceneEnvironment.tsx (43).** These read shader source.
Treat a shader string as the module's OUTPUT rather than its implementation:
assert against an exported shader constant instead of against the file. That
converts the reads without inventing an interface the GPU does not have.

**6. Everything at 44 and below, except CameraRig.tsx.** The unit components
(`UnitAbout`, `UnitBlog`, `UnitProjects`, `UnitTraining`, `UnitSystems`,
`ProjectArtifacts`) share one shape: the test wants to know what a shelf places
and where. Do them together behind one placement-and-interaction interface
rather than one at a time. The `CameraRig.tsx` batch is 41 wiring assertions
that are meant to be there plus 3 in `cameraZoom.test.ts`; skip it until a DOM
or r3f harness exists, then delete `policyWiring.test.ts` outright.

## Source reads kept on purpose

`src/app/components/stacks/policyWiring.test.ts` reads five component files and
makes 41 assertions against them. That is deliberate, and it is the one place
in this report where a bigger number is the better outcome.

Every assertion there says a component CALLS a policy module. None says what
the policy decides, because behavior tests already do: `freeRoamControls.test.ts`
for movement, look and the preference connector, `shelfDepthOfField.test.ts`
for the tuning, `Effects.contract.test.tsx` for the pass chain. `ChromeLayer`
installs its listeners from a `useEffect` and `CameraRig` runs inside an r3f
frame loop, so a server render executes neither, and this repo has no DOM
environment and no r3f harness. Without these the extractions could be silently
unwired and every behavior test would still pass.

Each assertion is one narrow token at one call site, so a rename inside a
policy module fails the test while ordinary editing around the call site does
not. Delete the file the day a harness can mount the two components.

## What the script cannot count

This is where the lower bound comes from. The script prints these two files
under "needs a hand check" rather than guessing at them, and their assertions
are corrected here and are NOT in the totals above. Add 6 to the total for a
true figure of 1058:

- `src/app/components/About.presentation.test.ts`, 1 assertion, against a
  regex match over the file.
- `src/app/components/stacks/scene/frameBudget.contract.test.ts`, 5
  assertions, against a comment-stripping helper applied to an object of reads.

`src/app/components/stacks/scene/metalShimmerBand.presentation.test.ts` reads
through a helper called with a loop variable. Its one assertion is counted, but
the batch shows as `unresolved`.

An AST version that followed taint through the TypeScript AST did resolve both
files. It was reverted: a fixed-point pass over every test in the tree ran long
enough to stall a run, against a report that has to be cheap enough to rerun
after every batch. The current script answers in under a tenth of a second, and
a lower bound plus six hand-corrected assertions is worth more than an exact
number nobody waits for.
