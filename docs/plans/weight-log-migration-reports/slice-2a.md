## Migration

`src/server/db/migrations/0023_weight_log.sql`, generated by `pnpm db:generate` and renamed from `0023_noisy_titania` (journal tag updated to match, `meta/0023_snapshot.json` added). Its journal `when` is later than 0022's, which is production's latest applied migration, so drizzle treats it as pending.

What the SQL does:

- Creates seven tables:
  - `weight_log_weigh_ins`: date primary key, pounds, `excluded` boolean, `updated_at`.
  - `weight_log_phases`: serial id, kind, start date, nullable end date. A null end marks the running phase.
  - `weight_log_planned_weeks`: week start primary key, phase id, nullable target and original target.
  - `weight_log_set_points`: position primary key, pounds.
  - `weight_log_scans`: date primary key, weight, lean mass, fat mass, BMC, reported body-fat %, the 15 regional columns, BMD, T-score, Z-score, A/G ratio, visceral fat, and the conditions note. Everything but weight is nullable.
  - `weight_log_body_fat_recollections`: id, date, low, high, note.
  - `weight_log_strength_history`: primary key (date, lift), value.
- Adds the foreign key from planned weeks to phases with `ON DELETE cascade`, a unique index on phase start, and an index on planned weeks' phase id.
- Appends five check constraints by hand, under a comment, because drizzle-kit 0.21 does not emit `check()` (0012 did the same):
  - pounds above 0 and at most 1500;
  - kind in bulk, cut, maintenance;
  - a phase starts on a Monday and ends on a Sunday after its start, or has no end;
  - a planned week starts on a Monday;
  - a recollection's range is ordered and within 0 to 100.

I read the generated SQL before applying it. It touches no existing table.

## Shortcuts

- The weekly-average parity compares the trimmed mean recomputed from the database against the snapshot's recomputed trimmed mean, not against Excel's saved weekly cells. The importer already checks those cells against the recomputed values on every run, so the chain holds.
- The import inserts phases one at a time to get their ids, and everything else in chunks of 500. That's fine for 3,000 rows. It is not built for repeated use.
- `scripts/weight-log/sources.ts` holds a small decrypt-only copy of the old AES-GCM format so the import and parity script can read `history-context.enc` and `snapshot.enc` after `encryption.ts` was deleted. It, `import.ts`, `parity.ts`, and `parity-check.ts` exist only for cutover and can be deleted afterwards.
