# Weight log

`/weight-log` is a public, read-only chart available by direct link, with no password required. It stays out of site navigation, search, and sitemaps. A dedicated 1200 × 630 share image and Open Graph / Twitter metadata describe the chart without including measurements. It opens on the full history with the seven-day trend and future weight plan enabled. The three body-fat layers start off, because a second axis beside the weight lines makes the chart hard to read; each has its own checkbox. The Layers control groups the other series into Weight and Body fat, with short group labels and a compact active legend. Future weight and future body fat have independent toggles; either can appear without the other or without historical body fat. The seven-day trend and main body-fat estimate use solid lines. A lighter dashed line identifies planned weight. Weight lines retain phase colors; body-fat lines, measured markers, and percentage-axis labels use purple. Lighter purple and different dash patterns distinguish early estimates and future body fat. Hidden series do not expand either axis. Layers and About open in privacy-masked shadcn popovers beside the phase and date controls. Layers has an explicit Close button, and selections persist when the panel closes. Popup state lives in the layer picker so opening or dismissing it does not rebuild the chart. Chart data is memoized independently of layer selection, and the DEXA plot and calendar skip unrelated parent updates. Range presets share one select. On mobile, range, Layers, and a Settings icon occupy one row; phase, exact dates, and calculation notes sit inside Settings. A small Weight / Body fat key replaces the expanded legends, with the full legend available in a popover. Reset zoom appears only when available on mobile. Desktop retains inline filters and expanded legends. The chart has a 600 px minimum width with horizontal touch scrolling on narrow screens. About this chart holds the calculation notes. Dragging across the plot with a mouse or pen zooms to the selected dates in either direction. Reset zoom restores the range before the first drag; manual date or phase changes establish a new range. Escape cancels a drag, and touch scrolling stays available. A horizontal hover guide snaps to the nearest visible series at the hovered date and labels its value in pounds or percent. Mouse clicks have no focus outline; keyboard focus remains visible. Phase, date, and range controls live inside Bodyweight over time and affect only that chart. The DEXA panel and year calendar retain their full histories. The page uses the same theme background and shared shadcn cards as Weightlifting, with lighter cards on the dark background. Both pages use 12 px outer padding on phones and 12 px card padding, with 8 px horizontal padding for the weight chart. Larger screens retain their existing spacing. Controls, checkboxes, and accordions use shared shadcn components, without summary-stat cards. Weightlifting and Weight Log share the collapsible section component, with the heading outside the card. The header shows elapsed years of recorded history and the Pacific (America/Los_Angeles) date of the latest weigh-in change, labelled Updated. The public payload carries no time of day. Drag instructions remain available to assistive technology without visible helper text. DEXA scan data, selected-scan details, bulk scenarios, and calculation notes are collapsed by default. Numeric scan-table cells use a blue-white-red scale independently for each metric; missing values remain uncolored.

The chart includes daily readings, workbook weekly averages, recorded targets, original targets, set points, a seven-day trend, a twelve-month rolling average, planned future weight, and a DEXA-based body-fat estimate. Bulking is red, cutting blue, and maintenance yellow. DEXA total-body checkpoints appear below it. Other scan methods are outside this version. The owner records and corrects weigh-ins on `/weight-log/edit`, described under Owner page.

The full-history calendar shows all 12 months of a selected year, with Monday-first weeks. Days after the last weigh-in show planned weights in faint gray when a dated projection exists, using the same daily interpolation as the chart. The year picker extends through the plan. Historical gaps and days without a plan remain blank; actual weigh-ins take precedence. Planned values do not affect the weigh-in count or color scale, and their tooltips identify them as planned weights. Its blue-white-red scale uses the minimum, midpoint, and maximum of all recorded weigh-ins. Changing the year or chart filters never rescales those colors. Hover, focus, or tap a recorded day for a formatted tooltip containing its weight, weekly average, target, trend sample count, annual average, and body-fat estimates. Tapping the open day again or pressing Escape closes it. There is no separate day-details footer or visible color-scale legend. Tooltip portals carry the same privacy masking classes as the page. Calendar state stays in memory.

Main-chart data lines use phase colors, with solid weekly averages, long-dashed seven-day trends, dotted twelve-month averages, short-dashed targets, dotted original targets, and longer-dashed future plans. Body-fat estimates use dash-dot lines between scans, dotted lines after the latest scan, and round dots for future values. Global set-point guides stay neutral. Continuous lines change color at dated phase boundaries; when phase templates overlap, the latest start takes precedence. Dates without an assigned phase are gray. Each phase's separate weekly and target lines keep its own color. SVG gradients use the resolved time axis so cropping, resizing, flat lines, and sparse data retain the same phase boundaries.

## Storage

The data lives in Postgres, in seven `weight_log_` tables defined in `src/server/db/schema.ts` (migration `0023_weight_log.sql`). The `wl_` prefix already belongs to weightlifting.

- `weight_log_weigh_ins`: one row per date, with pounds and an `excluded` flag. Weigh-ins are independent of phases and belong to whichever phase covers their date.
- `weight_log_phases`: kind (`bulk`, `cut`, or `maintenance`), a Monday start, and a Sunday end. A null end marks the running phase. Phases never overlap. There is no name column: the site derives names like "Bulk Aug '26 - Aug '27" from kind and dates, and a running phase uses its last planned week as the end.
- `weight_log_planned_weeks`: one row per Monday, with its phase, target, and original target.
- `weight_log_set_points`: the set-point guides, by position.
- `weight_log_scans`: DEXA scans with every workbook column, including bone mineral content, the regional panel, BMD, T- and Z-scores, the A/G ratio, visceral fat, and the conditions note. The regional panel exists for only some scans, so its columns are nullable.
- `weight_log_body_fat_recollections` and `weight_log_strength_history`: the historical context behind the early body-fat estimate.

`getWeightLog()` in `src/lib/weight-log/data.ts` reads every table in one repeatable-read, read-only transaction and builds the `WeightLog` DTO in `records.ts`. Weeks with weigh-ins but no planned row still appear, with no target. `importedAt` and `sourceModifiedAt` both report the latest weigh-in change.

## Owner page

`/weight-log/edit` is where the owner records weigh-ins and edits the plan. Signed out, it shows only a centered card with the Google sign-in button. Signed in as `OWNER_EMAIL`, it shows the weekly table, which is also where weigh-ins and weekly targets are typed. The running phase's plan and the set points have pages of their own, `/weight-log/edit/plan` and `/weight-log/edit/set-points`, at every width, so a phone never gets a sheet or a modal. The header holds the title, which links back to the chart and turns its barbell into an arrow on hover as the chart's title does, then a nav with Weeks, Plan, Set points, and Sign out. On the Weeks page the table puts its phase picker and Go to date in that header, through a portal into a slot the header leaves for them. At 1024 px and wider the header is one row. Narrower, the picker and Go to date take a second row, and below 640 px the nav links and Go to date show only their icons, each named by a Tooltip and an accessible label. The table is the page's main content: it doesn't fold and has no heading. All three pages share one server-side session check (`ownerPage.tsx`). Every read and write goes through the `weightLog` tRPC router (`src/server/api/routers/weightLog.ts`), and every procedure there is on `ownerProcedure`. `weightLogOwnerOnly.test.ts` and `ownerDataBoundary.test.ts` enforce both rules.

- The weekly table follows the workbook's phase tabs: Monday to Sunday, then weekly average, change from the previous calendar week's average (across a phase boundary), target, average minus target, lb/wk (target minus the previous week's target in the same phase, shown to two decimals), original target, and target minus original target. It opens on the phase that holds today, at the top of the page, with today's cell outlined in red, and a picker lists the other phases by their derived names. Weeks past the plan with weigh-ins appear with no target. The days are colored as the workbook's tabs are: weigh-ins white to green across the phase, and Average, Target, and Original target on one shared blue-white-red scale. Excluded weigh-ins are struck through and uncolored. The scale math is in `src/lib/weight-log/color-scale.ts`.
- The table edits like a spreadsheet. Tapping a day, a target, or an lb/wk turns that cell into an input of the same size, with the caret at the end and nothing selected, because a backspace on iOS clears a fully selected field. Return or leaving the cell saves, Escape cancels, and an unchanged value sends nothing. On a desktop, Tab and Shift+Tab move between editable cells. On a touch screen the cells are wider and taller and the input's text is 16 px, so iOS doesn't zoom the page. The rules for what a typed number sends are in `src/lib/weight-log/sheet.ts`.
- A day cell saves its weigh-in through `upsertWeighIn`, rounded to one decimal as the server rounds it. A date holds at most one weigh-in, so typing over one replaces its pounds and keeps its `excluded` flag. Emptying a day deletes its weigh-in, and its `excluded` flag goes with it. Days after today on the device's clock take nothing. Today's cell has a red outline, and when it has no weigh-in it opens on the latest counted weigh-in before it, muted, with "Filled in from yesterday. Not saved yet." Return saves that carried value; leaving the cell without typing saves nothing. Other empty days open blank.
- Target and lb/wk are one edit (decision 11). Typing an lb/wk sends `changeRate`, and typing a target sends the rate that reaches it, the target minus the previous week's target. A typed lb/wk is rounded to two decimals. A target's rate keeps six decimals, as the server keeps targets, so the saved target is exactly the one typed. Either way the week's target becomes the previous week's target plus the rate, and every later target in the phase moves by the same amount. A target can be at most 10 lb from the week before. A phase's first week has no previous week, so its target and lb/wk are read-only, as is any week without a target. Original targets never change.
- One status line floats near the bottom of the screen for the whole table. It reports the last change and offers Undo, one level deep: Undo puts a replaced weigh-in's pounds back, deletes a weigh-in the change added, or sets the week's old lb/wk exactly, which moves its target and every later one back. A deleted weigh-in comes back through `restoreWeighIn` with the excluded flag it had. That procedure only fills an empty date and refuses one that has a weigh-in again, so it can't change a flag on a row that exists (decision 14 still holds). Every write settles through its own promise, so two quick edits each clear their own cell and record their own Undo, and Undo waits until nothing is in flight. A refusal shows the server's message, such as a stale plan, and the cell keeps what was typed, in red, until it saves or Escape clears it. A sent value shows muted in its cell until the table reloads, and while a plan edit is landing the target and lb/wk cells wait.
- Go to date, beside the phase picker, opens any date up to today. A date in a phase switches the table to that phase and opens the day. A date outside every phase opens in a separate one-row table labeled "Outside every phase", so a weigh-in can still be added or fixed there. That calendar week comes from `weightLog.week`, which reads by date, not by phase. This week also gets a row before it has a plan or a weigh-in, for example when the running phase's plan has ended.
- Plan shows the running phase and edits its length. Length sets the plan's number of weeks: more weeks continue at the last week's lb/wk (flat when the plan has one week), and fewer weeks come off the end. The server refuses to remove a week that holds weigh-ins and names it. Only the running phase's length can change; an ended phase ends where the next one starts.
- Start a phase takes a kind, a start Monday, a starting target, an lb/wk, and a number of weeks, and asks once before it ends the current phase. The current phase ends the day before the new start. Its planned weeks before the start stay. Every planned week on or after the start leaves it, with or without weigh-ins: weeks the new plan covers take the new plan's target, and empty weeks past the new plan are deleted. The new plan has to run through every week on or after its start that holds weigh-ins, so no weighed-in week loses its row. A start on the current phase's own Monday replaces that phase. The server accepts any Monday on or after the current phase's start; the picker offers twelve weeks back through 26 weeks ahead. The confirmation describes the plan the page loaded. If a refetch brings a different current phase or a changed plan while it is showing, the red button goes away and the page asks the owner to check the details and tap Start again.
- Original targets follow decision 12. A new phase's weeks get original targets equal to their targets, including weeks moved from the old phase, since the original target belongs to the phase that wrote it. Rate changes never touch them, and weeks added by Length have none. A week removed from the end and added again counts as added.
- Set points are an ordered list of pounds. Saving writes the whole list, numbered from 1, since the chart labels them Set point 1, Set point 2, and so on. The save also sends the list the edit started from. If another tab saved a different list in the meantime, the server refuses, and the owner cancels to see the new list before editing again.
- Every plan edit sends the revision of the plan the page showed, a hash of every phase and planned week from `planRevision`. A rate change also names the phase the page showed the week in. If another tab or a phone changed the plan since, the server refuses with "The plan changed since this page loaded it", writes nothing, and the page refetches so the owner sees the current plan. Weigh-ins are not part of the revision, so recording one does not make a plan edit stale.
- The plan math lives in `src/lib/weight-log/plan-edits.ts`. Each planner returns the rows to change, and the router writes them in one transaction under an advisory lock (`PLAN_LOCK`), reading weigh-ins without writing them. Set point saves take the same lock, so two saves at once run in turn. Starting targets and set points are rounded to one decimal before the server checks that they are above 0, so 0.01 is refused rather than saved as 0. `planViolations` names any overlap between phases, a running phase before another phase, or a planned week outside its phase, and the tests run it after every kind of edit and after a seeded run of random edits. Targets and rates keep six decimals, and starting targets and set points one. The page shows lb/wk to two decimals and rounds a typed lb/wk to two.

The public chart is `force-dynamic` with no shared cache, so a saved weigh-in appears there on the next request. Strength at Bodyweight caches its analysis for five minutes (`src/server/queries/weightliftingPareto.ts`), so a new weigh-in reaches it within five minutes.

## Entry from a Shortcut

The owner's Log Weight Shortcut records the day's weigh-in from the iPhone without signing in, then shows the week as a notification. It is the one way to write owner data besides Google sign-in (plan decision 38), so its token can do very little. The Shortcut's recipe is the "Log Weight" section of `~/Desktop/Agents/apple-health/shortcut/RUNBOOK-iphone.md`.

- `POST /api/weight-log/weigh-in` takes a JSON body such as `{ "date": "2030-01-08", "pounds": 150.2, "replace": false }`. The date is the phone's own. Pounds may be a number or a numeric string, and the server rounds them to one decimal place. Every expected outcome answers 200 with a `status`, so the Shortcut branches on a field rather than a status code. `saved` means the date had no weigh-in. `exists` means it has a different one and nothing was written; the answer carries `previous` and a `question` for the Replace prompt. `replaced` means `replace` was true and the pounds changed, with the `excluded` flag kept. `unchanged` means the date already had those pounds, so a retried request does nothing. Every 200 carries `title`, the outcome in a few characters for the notification's title: "✓ 150.2" saved, "↻ 150.2, was 150.6" replaced, "= 150.2" unchanged, and "Kept 150.6" on `exists`. When the date's weigh-in is excluded, the title ends " · excluded", and `question` says so and that a new value stays excluded. Every 200 also carries `summary`, the week in one line for the body: "Avg 150.4 · 0.4 over target", "· on target" when the gap rounds to zero, "Avg 150.4" alone past the plan's end, "No average yet" when nothing counts toward the week, and "Week unavailable" when the save worked but the week couldn't be read. It is never empty, because the first version of the Shortcut treats a missing `summary` as a failed request (plan decision 40). `question` reads "Today has 150.6. Replace with 150.2?". It says "Today" only when the date is today in Los Angeles (`ownerToday`), and names the date, such as "Mon, Nov 9", otherwise, since the server can't know the phone's date. A bad body or a date outside the window answers 400, a failed save 500, and every other method, OPTIONS included, 405 with `Allow: POST`.
- `GET /api/weight-log/week-card?date=YYYY-MM-DD` answers a PNG snapshot of the Weeks table on `/weight-log/edit`: its header row, then the previous calendar week's row and the row of the week holding that date, with that date's cell ringed in red as today. The rows read and color exactly as the editor's do (`WeekCard.test.tsx` renders both and compares them). Each row takes its colors from the table that holds it, so last week in another phase keeps that phase's scales, and its `#` counts weeks in that phase. A week outside every phase is colored on its own, as the editor shows it on a plain load. A week the log lacks joins the table of the phase that holds it, as the editor adds this week before anything is in it. The previous row is left off when no phase holds it and it has no weigh-ins, as in the log's first week. A small caption names each row's phase with the picker's color dot, or says "Outside every phase". The card copies the editor's light theme at a phone's width and twice its pixel density: SF Pro Display at 12 px, the same fills, rules, and the red ring, about 1310 by 300 pixels. It draws the editor's columns except Orig and its Gap (`CARD_COLUMNS`), because an expanded notification shrinks the card to about 350 pt wide, which puts its text near 6 pt. `week-card.ts` builds the rows, and the editor and the card share the column definitions and formatters (`week-columns.ts`, `format.ts`). The card is always light, because a notification image does not follow dark mode. When the weigh-ins or the fonts can't be read, it answers a JSON 500, `{ "error": "The week card could not be drawn." }`, with the same headers as every other answer. `next.config.js` traces the two SF Pro Display files in `src/fonts/weight-log/` into the route, so it reads them from disk once per warm function. `scripts/generate/weight-log-card-fonts.py` makes them from the installed fonts, with tabular figures built in, since satori can't turn on `tnum`.
- Both routes answer only `Authorization: Bearer <WEIGHT_LOG_ENTRY_TOKEN>`, and both answer 503 to everything while the variable is unset, which it is everywhere but Vercel Production. The token is separate from the Health mirror's `WEIGHT_LOG_MIRROR_TOKEN`. When both are set to the same value, `src/env.js` fails validation and the build stops.
- The token's scope is enforced on the server. It writes a weigh-in only for a date that is today or yesterday in some real time zone, from UTC−12 to UTC+14 (`shortcutWindow` in `src/lib/weight-log/weigh-ins.ts`). The earliest date is yesterday in UTC−12 and the latest is today in UTC+14. The phone sends its own date, so today and yesterday are always accepted wherever the owner is, and a date that has not begun anywhere is refused. It never deletes and has no route to phases, plans, or set points. The card answers only for a date in the same window. A leaked token can change at most four dates, each visible and fixable on `/weight-log/edit`.
- Saves go through `saveWeighIn` in `src/lib/weight-log/weigh-ins.ts`, the same function the owner page's `weightLog.upsertWeighIn` calls with `replace: true`. It takes the shared plan lock, locks the date's row, and then inserts, updates, or does nothing.
- Every answer, refusals included, sends `Cache-Control: private, no-store, max-age=0`, `X-Robots-Tag: noindex, nofollow, noarchive`, and `X-Content-Type-Options: nosniff`. The token travels only in the header, never the URL. A failure logs its step and the error's code, never the body or the row, and reports the same line to PostHog error tracking as a new error, so the original message never leaves the function.
- `src/app/api/weight-log/routes.guard.test.ts` lists every route under `src/app/api/weight-log/` with the token it answers. Every method Next answers for the route, including the HEAD and OPTIONS it adds when a route leaves them out, must refuse no token, a wrong one, and the other route's token before the database is touched, both with an empty request and with one the route would otherwise serve. A 405 must carry `Allow` and the no-store headers. A new route there fails the test until it is listed.

## Importing the workbook

The workbook stays in iCloud as the archive. The import is a one-time move into the database, run on cutover day after the morning weigh-in. Weigh-ins after that go in through `/weight-log/edit`, and a reading entered in the workbook after the import must be re-entered by hand.

The import writes everything in one transaction. `--expect-host` must match the host in `DATABASE_URL`, so the command cannot write to a database you did not name. It refuses to run when any `weight_log_` table already holds rows. `--replace` deletes the existing rows first, inside the same transaction, but refuses while the database holds a weigh-in whose date the workbook export lacks or whose pounds differ from it. After cutover those are site entries, and the workbook cannot restore them. The refusal names their count and dates. `--discard-site-entries` overrides it. A real run first takes the plan editor's advisory lock (`PLAN_LOCK`), so it waits for a plan or set point edit in progress and edits wait for it. Without that, an import and a phase start could each hold rows the other needs, and Postgres would cancel one of them as a deadlock. It then locks `weight_log_weigh_ins` in EXCLUSIVE mode before that check and holds both locks until it commits, so a save from `/weight-log/edit` during the import waits and then lands on top of the imported rows instead of being deleted. The public page keeps reading meanwhile. `--dry-run` runs every check, including the `--replace` guard, in a read-only transaction, takes neither lock, and writes nothing. `--history-context` is the old encrypted companion holding the recollection and strength summaries, decrypted in memory with `NEXTAUTH_SECRET`; a plain JSON file also works. The import prints only counts, the running phase's name, and the dates of trimmed weeks.

On the way in it applies the phase rules. Every phase must start on a Monday and be a bulk, cut, or maintenance. Each phase ends the day before the next one starts, and its planned weeks from that day on are dropped when they hold no weigh-ins. A dropped week that holds a weigh-in stops the import. A date has at most one weigh-in, and the one excluded reading keeps its flag.

The parity check is read-only. It runs `import_workbook.py` on the same workbook the import read and requires exact equality with that export for every weigh-in, exclusion, scan value (including the added scan columns), set point, target, original target, and weekly average in the weeks kept. The recollection and strength readings must match the old encrypted snapshot, which is their only other copy. It lists decision 26's intended differences by name: the trimmed weeks and shortened phase ends, the derived phase names, the removed `other` kind, and the added scan columns. Anything else is printed as a date and field name, never a value, and makes it exit 1. It also compares the database with the old snapshot and prints those differences without failing, because the snapshot changes only when the Hermes job uploads. Pass parity the same `--exclude-sheet` values the import's export used. Its tests use synthetic data and run in `pnpm verify`.

## Workbook importer

The importer keeps actual date cells, daily weights, phase boundaries, target values, and the days included in each weekly calculation. It checks recomputed averages against Excel's saved values. Formula-specific exclusions survive import; excluded readings remain visible. Nonnumeric daily annotations are counted and skipped. No formulas are evaluated as code. DEXA values come from the `BF%` sheet: the total-body row with reported body-fat overrides, bone mineral content, and the conditions note, plus the regional, bone-density, and visceral-fat panel for the scans that have it. A zero in that panel is kept as zero.

Dates come from workbook cells, even when a copied tab has a newer name. To omit an unfinished tab after reviewing it, pass `--exclude-sheet "Sheet name"` to the importer. Correcting a mislabeled date before the import requires changing the source workbook and importing again.

## Analysis choices

The seven-day trend adapts the trimmed mean in `WeightliftingApp-AnalyzeData/src/analysis_utils.py` for sparse logging. At each weigh-in, it uses available readings from that day and the preceding six calendar days. With three or more readings, it removes one highest and one lowest. It linearly bridges trend anchors at most 14 days apart. Longer gaps remain empty, and the observed trend never extends past the last weigh-in. Selecting a calendar day shows its trend sample count. Raw readings and workbook weekly means remain separate series.

The twelve-month average is the arithmetic mean of recorded weigh-ins in the interval after the same calendar date one year earlier through the current day. February 29 uses February 28 as the prior-year boundary. It uses partial history at the beginning, omits missing readings, leaves empty twelve-month windows blank, and stops at the last actual weigh-in. Like the seven-day trend, it is computed before filtering.

The date axis uses January 1 markers for ranges of at least two years, month or quarter starts for medium ranges, Mondays for shorter ranges, and days for close views. Each marker has a vertical gridline. The weight grid uses one-pound steps with five-pound major lines and labels; its bounds follow only visible weight series and set points.

Set points come from consecutive cells beneath the aggregate sheet's `Set Points` header. Future weight uses the workbook's explicit weekly targets, interpolated in time within each phase. It is a plan, not a trend extrapolation. The main chart distinguishes these dashed future lines from historical targets and marks the last weigh-in. Original target values remain available as a separate comparison.

The body-fat axis starts at 4% and ends at the next whole percentage above the visible values, with a quarter-point minimum margin. Hidden projections do not expand its range. When only body fat is visible, horizontal gridlines and labels use 1% steps, with stronger lines and labels at multiples of 4%. Missing measurements never render markers.

The body-fat overlay uses a transparent visualization heuristic. At scan anchors, fat-free mass equals scan weight multiplied by one minus the reported body-fat fraction. This includes bone and preserves reported percentage overrides. Between scans, fat-free mass interpolates linearly in time. Smoothed scale weight receives an interpolated offset between the two scan dates, making the curve meet both DEXA readings. Missing smoothed weight leaves a gap. Earlier dates have a separate optional layer described below. This is retrospective interpolation, so adding a later scan can revise estimates between scans.

### Early body-fat estimates

The default-off `Early body fat · exploratory` layer reconstructs history between a provisional recollection and the first usable DEXA. It uses phase colors, a faint dotted center line, and a shaded envelope of alternative histories. Recollections are labeled separately from scans. Hovering shows the center and full range. The percentage axis retains its 4% floor, clipping lower band values visually without changing them. Fitting happens before date filters and zooming.

The DTO's optional `historicalContext` field, built from the recollection and strength-history tables, contains a dated body-fat range, its provenance note, and comparable strength readings. A recollection needs a matching scale weight to establish starting fat-free mass. An approximate date must be disclosed in the note, especially when the recollection predates the first recorded weight. Missing context produces no early curve. No personal assumptions or fitted values belong in source code or test fixtures.

`historical-body-fat.ts` converts each end of the starting range into fat-free mass using the weight at that date. The center line starts at the midpoint of the recollection and reaches the first DEXA's reported composition. Fat-free mass can change over time, so revisiting the same weight no longer implies the same body composition. The scale correction fades from zero at the starting recollection to the scan-to-scale difference at the DEXA. Missing smoothed weights remain gaps, and dates outside the two anchors receive no early estimate.

The central progress curve is half calendar time, one quarter cumulative weight gain during recorded bulks, and one quarter sustained strength progress. Strength uses the median session performance within 90 days on either side of each date, requiring at least three sessions per lift. Only comparable lifts with at least 5% endpoint improvement participate; at least two must be available at a date. Normalized log progress is bounded from zero through one, and a running maximum reduces the effect of temporary performance dips. Unsupported dates fall back to time. Strength only distributes the assumed endpoint change over time; it does not convert lifting performance into pounds of muscle. The imported performance summary uses comparable variations and low-repetition sets.

A 28-day mean of available weight trends supplies cycle changes. The existing DEXA gain/loss partition model assigns a possible fat-free component to those changes. For any progress path `p`, the cycle adjustment is `cycleShare * (cumulativeCycleFFM - p * finalCycleFFM)`, keeping both endpoint constraints intact. The center uses half this adjustment. This permits changes through bulks and cuts without replacing the endpoints with the later training-period regression.

The shaded envelope spans both ends of the recollection, calendar, front-loaded, delayed, bulk-informed, and strength-informed progress paths, zero/half/full cycle adjustments, and a DEXA endpoint sensitivity of plus or minus two percentage points. Impossible compositions are omitted. The center is always included in the envelope. This is a set of conditional scenarios, not equally likely outcomes or a confidence interval. The former backward scan-prediction score is removed because it did not validate reconstruction of earlier muscle gain. No numerical probability or coverage is assigned to this envelope.

Strength and lean-mass changes can have weak associations over a training block, as shown in [Bagheri et al.](https://pubmed.ncbi.nlm.nih.gov/39206316/). Hydration and glycogen also affect DEXA lean-mass measurements, as shown in [Toomey et al.](https://pubmed.ncbi.nlm.nih.gov/28204901/). These findings explain why performance is supporting evidence and why the paths remain explicit assumptions. Neither study validates this reconstruction.

The recollection and strength summaries live in `weight_log_body_fat_recollections` and `weight_log_strength_history`, apart from the weigh-ins. The import fills them from the old `history-context.enc` companion and fails on invalid or undecryptable context rather than silently dropping it. When the DTO builder finds several recollections, it uses the earliest.

After the last scan, the model uses `FFM = anchor FFM + k * weight change`, the relationship in the analysis repo's `src/dexa/forecast.py`. Separate gain and loss values of `k` are medians of consecutive scan ratios. Intervals with less than 2 lb of change, more than 365 days between scans, or a ratio outside zero to one are excluded. With fewer than two usable intervals in a direction, FFM stays constant and the interface states that fallback. Planned future weight drives a separate dashed body-fat projection. Impossible percentages are omitted rather than clamped. These are heuristic estimates, not daily measurements or validated predictive intervals. The main time-series chart does not reproduce the analysis repo's bootstrap forecast or the workbook's Bull/Bear scenarios.

The DEXA panel plots lean soft tissue against bodyweight, adapting `WeightliftingApp-AnalyzeData/src/dexa/calculations.py` and `src/dexa/charts.py`. Numbered scans follow chronological order, with red gain arrows and blue loss arrows. The dashed least-squares trend uses all scans with lean mass; a dotted line connects the latest two complete consecutive scans. Vertical bars show signed residuals. The panel preserves scan numbers, interval efficiencies, and the full-history fit independently of the bodyweight chart filters. Missing lean mass leaves a gap. Selecting or focusing a scan shows its values and interval efficiency, defined as lean gain divided by weight gain for bulks and one minus lean loss divided by weight loss for cuts. No ratio is shown for unchanged weight.

Body-fat contours use one percentage-point steps and hold bone mineral content constant. The database stores each scan's bone mineral content, but the DTO does not carry it yet, so the panel infers it from the latest scan’s weight minus lean and fat mass. It omits contours if those components are missing or the remainder is nonpositive. Reported body-fat overrides do not change this reference. The measurements table retains scans with missing lean mass.

The DEXA chart also projects the current bulk to 240 lb, anchored at the latest scan. A checkbox toggles the overlay; it appears only when the date range includes that scan. The expected path is the median, with a ribbon from the 2.5th to 97.5th percentiles and best/expected/worst endpoint values. Best and worst are percentile scenarios, not absolute limits. Body-fat scenarios use the same inferred bone mass as the contour lines.

`src/lib/weight-log/dexa-projection.ts` adapts the block-bootstrap mean plus future-interval residual from the analysis repo's `src/dexa/forecast.py`, using lean soft tissue directly. It uses consecutive positive-weight scan intervals with at least 2 lb gained, at most 365 days between scans, and complete lean measurements. Observed ratios are not clipped. Intervals sharing a scan are resampled together. Twenty thousand seeded draws combine the resampled mean with one observed centered residual to capture variation in a future bulk as well as uncertainty in the fitted average. The chart requires at least three usable intervals across three scan groups. It omits degenerate or physically invalid bounds and targets more than 60 lb beyond the anchor.

This is a conditional model prediction interval, not a validated 95% coverage claim. It holds the latest scan exact, includes observed scan variation in the historical ratios, and adds no separate measurement-error model. The ribbon therefore narrows to zero at the anchor. It assumes constant lean gain per pound and that the next bulk resembles prior bulks. The UI states the sparse interval count, exclusions, and these limitations. The distinction between a fitted-mean confidence interval and uncertainty for a future outcome follows [NIST's prediction-interval guidance](https://www.itl.nist.gov/div898/handbook/pmd/section5/pmd512.htm).

The calculation tests verify scan-anchor agreement, sparse sampling, gap limits, separate observed and planned values, and fallback behavior. All model inputs come from the Weight Log tables. Filtering the chart never recalibrates the model or changes its historical context.

Workbook weekly means use available readings in the recorded weekly range, trimming one extreme at each end only when at least three remain. The chart displays each weekly mean across that week. It preserves empty calendar weeks rather than drawing through missing history. The DEXA panel follows the analysis project's distinction between lean soft tissue and bone mineral content; it does not substitute fat-free mass for lean mass.

## Access and storage

- The page and server-only data loader allow anonymous reads. There is no public data API or static data import.
- Production and local development read the `weight_log_` tables at request time through the site's existing `DATABASE_URL`. No other credential is involved, and no measurement is stored in the repository, S3, or build output.
- The route is dynamic, uses no shared data cache, and sets private/no-store, noindex, no-referrer, and frame-denial headers. Metadata contains no measurements. The route is absent from public search and sitemaps. No chart state or readings go into analytics, URLs, or browser storage.
- `pnpm check:weight-log-boundary` runs after builds. It fails if the route was prerendered, which would freeze measurements into build output, if a workbook entered the Git index, public assets, or a server file trace, or if the chart DTO entered public assets.
- Strength at Bodyweight reads the same tables through `getWeightLog()`, and `pnpm refresh:lifting-pareto` reads them directly.

The server-only data and DTO boundary follow the [Next.js data-security guidance](https://nextjs.org/docs/app/guides/data-security).
